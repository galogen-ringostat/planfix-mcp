## Axis 5 — error handling / retry policy

| ID | Finding | Evidence | Severity / risk |
|---|---|---|---|
| **E1** | **`planfixRequest` retries 429/5xx/timeouts for ALL calls — including non-idempotent writes.** A timeout or 5xx AFTER the server committed a write, retried by the client, double-creates: duplicate time entries (double-logged hours), duplicate comments/tasks/estimation entries. `log_workday`/`add_estimation` promise "writes are NEVER retried automatically (double-count risk)" at the TOOL level (`timeentries.ts:340`, `customfields.ts:272`) while the client retries under them — the promise is currently false in the 5xx/timeout window. Code-22 and HTTP-429 retries are safe (logical/pre-commit refusals); 5xx/timeout retries of mutating POSTs are not. `planfixUploadFile` already implements single-attempt for exactly this reason — policy is inconsistent across the two entry points | `client.ts:93-98` (5xx retry), `:104-107` (timeout retry), vs `:126-131` upload doc | **critical** / behavior-changing (proposal: retry-policy flag on planfixPost — mutating call sites opt out of 5xx/timeout retry, keep 429+code-22; audit each of the ~14 write sites) |
| E2 | `planfixUploadFile` parses the body BEFORE checking `response.ok` — a non-JSON error body (HTML 502 from a proxy) surfaces as a raw `SyntaxError`, not "Planfix HTTP 502". `planfixRequest` checks `.ok` before parsing — drift between entry points | `client.ts:144-147` | cleanup / behavior-preserving (error path only) |
| E3 | `file/from-url/` uploads run through the retrying `planfixPost` → a 5xx retry can double-create an orphan file | subsumed by E1 | covered by E1 |
